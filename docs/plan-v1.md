# Oxygen Not Included 멀티플레이 모드 개발 계획

## 1. 문서 개요

이 문서는 《Oxygen Not Included》에 멀티플레이 기능을 추가하기 위한 기획 및 개발 계획서다.

핵심 콘셉트는 다음과 같다.

> 하나의 소행성 안에서 각 플레이어가 자신만의 프린팅 팟과 복제체를 운영하고, 자원과 인프라를 연결해 공동 생존하는 협동형 멀티플레이 모드

초기 버전은 기존 공개 멀티플레이 모드의 네트워크, Steam 연결, 명령 동기화, 세이브 기반 하드 싱크 구조를 최대한 활용하고, 그 위에 플레이어별 소유권과 프린팅 팟 시스템을 추가하는 방식으로 개발한다.

---

## 2. 프로젝트 목표

### 2.1 핵심 목표

- 2~4명이 하나의 월드에서 함께 플레이할 수 있다.
- 플레이어마다 프린팅 팟을 1개씩 소유한다.
- 플레이어마다 자신의 복제체를 소유한다.
- 자신의 복제체와 개인 시설만 직접 관리할 수 있다.
- 공동 시설과 공동 자원은 권한에 따라 공유할 수 있다.
- 세이브, 로드, 재접속, 하드 싱크 이후에도 소유권이 유지된다.
- 기존 싱글플레이 동작을 최대한 유지한다.
- 초기에는 별도 전용 서버 없이 호스트 권위형 구조로 동작한다.

### 2.2 비목표

MVP 단계에서는 아래 기능을 구현하지 않는다.

- 플레이어 간 PvP
- 프린팅 팟 파괴
- 공개 매치메이킹
- Steam 외 플랫폼 지원
- 전용 서버 상시 운영
- 모든 DLC 및 모든 외부 모드 호환
- 호스트 마이그레이션
- 플레이 도중 무제한 신규 플레이어 참가
- 자연 타일과 모든 자원에 대한 개별 소유권
- 완벽한 결정론적 시뮬레이션

## 3. 게임 기획

## 3.1 기본 플레이 구조

| 항목 | 기본안 |
|---|---|
| 최대 인원 | 2~4명 |
| 월드 | 하나의 소행성 |
| 시작 위치 | 플레이어별 분리된 시작 구역 |
| 플레이어별 시작 시설 | 프린팅 팟 1개 |
| 플레이어별 시작 복제체 | 3명 |
| 복제체 소유권 | 생성된 팟의 소유자에게 귀속 |
| 연구 | 전체 공유 |
| 자연 자원 | 공동 |
| 건물 | 개인, 연합, 공동 권한 |
| 승리 조건 | 공동 생존 및 우주 진출 |
| 서버 구조 | 호스트 권위형 |
| 세이브 위치 | 호스트 로컬 |

## 3.2 초반 진행

각 플레이어의 프린팅 팟은 서로 일정 거리 이상 떨어진 위치에 생성된다.

각 시작 구역은 최소한의 생존이 가능해야 한다.

- 산소 생산 자원
- 물
- 초반 식량
- 기본 금속
- 화장실 및 침실 공간
- 굴착 가능한 연결 경로

초반에는 각자 식민지를 안정화하고, 중반부터 다른 플레이어의 식민지와 연결한다.

## 3.3 식민지 연결

서로의 구역이 연결되면 다음 기능을 사용할 수 있다.

- 자원 요청
- 공동 저장고
- 공동 건설 프로젝트
- 복제체 통행 허가
- 전력망 연결
- 액체 및 기체 파이프 연결
- 지도 핑
- 식민지 상태 공유

## 3.4 프린팅 팟

프린팅 팟은 플레이어 식민지의 중심 시설로 사용한다.

프린팅 팟 기능:

- 소유 플레이어 식별
- 복제체 출력
- 소속 복제체 목록
- 식민지 이름 설정
- 권한 관리
- 재접속 기준점
- 자원 요청
- 공동 프로젝트 승인
- 플레이어 전멸 시 복구

기본 협동 모드에서는 프린팅 팟을 파괴할 수 없도록 한다.

## 3.5 복제체 소유권

복제체는 자신을 출력한 프린팅 팟의 소유자에게 귀속된다.

소유 플레이어만 다음 기능을 사용할 수 있다.

- 직접 이동 명령
- 스킬 지정
- 작업 우선순위 변경
- 스케줄 변경
- 음식 및 소비품 설정
- 이름 변경

다른 플레이어는 해당 복제체의 상태를 확인할 수 있지만, 기본적으로 설정을 바꿀 수 없다.

## 3.6 건물 권한

건물과 저장고에는 다음 권한을 부여한다.

### 개인

소유자만 설정, 해체, 자동화 변경이 가능하다.

### 연합

지정된 플레이어만 조작할 수 있다.

### 공동

모든 플레이어가 사용할 수 있다.

### 잠금

소유자의 승인 전까지 설정 변경과 해체가 불가능하다.

## 3.7 자원 공유

자원 자체에 소유권을 붙이지 않고 저장 위치와 접근 권한으로 관리한다.

저장고 유형:

- 개인 저장고
- 연합 저장고
- 공동 저장고

자원 요청 예시:

- 조류 2톤 요청
- 정제 철 500kg 요청
- 음식 100,000kcal 요청
- 산소 긴급 지원 요청

## 3.8 시간 배속

멀티플레이 환경에서는 시간 제어 충돌을 방지해야 한다.

권장 규칙:

- 1배속: 누구나 변경 가능
- 2배속: 과반수 동의
- 3배속: 모든 활성 플레이어 동의
- 일시정지: 누구나 긴급 정지 가능
- 장시간 정지 시 과반수 동의로 재개
- 접속 종료 또는 심각한 위기 발생 시 자동 1배속

## 3.9 플레이어 접속 종료

플레이어가 나가면 소속 복제체는 오프라인 관리 모드로 전환된다.

- 기존 생명 유지 행동 지속
- 신규 대형 건설 작업 중지
- 위험 구역 진입 금지
- 다른 플레이어의 직접 조작 금지
- 지정한 대리 관리자에게 제한적 권한 부여 가능

## 3.10 플레이어 전멸

한 플레이어의 복제체가 모두 사망해도 전체 게임은 종료되지 않는다.

해당 플레이어의 프린팅 팟은 휴면 상태로 전환된다.

다른 플레이어가 자원을 투입하면 복구할 수 있다.

- 전력
- 식량
- 산소
- 정제 금속
- 데이터 뱅크

복구 시 새로운 복제체 1명으로 재시작한다.

## 4. 기술 전략

## 4.1 개발 접근

완전히 새 멀티플레이 엔진을 만드는 대신 기존 ONI 멀티플레이 오픈소스 프로젝트를 포크해 확장한다.

우선 검토 대상:

- `onimp/oni_multiplayer`
- `Lyraedan/Oxygen_Not_Included_Together`

우선순위:

1. 기존 프로젝트 빌드 성공
2. 네트워크 구조 분석
3. Steam 연결 및 하드 싱크 유지
4. 플레이어 소유권 계층 추가
5. 프린팅 팟 및 복제체 분리
6. 권한 시스템 추가
7. 장시간 안정화

## 4.2 기본 기술 스택

| 영역 | 기술 |
|---|---|
| 언어 | C# |
| 게임 런타임 | Unity Mono |
| 프레임워크 | .NET Framework 4.7.x |
| 게임 패치 | Harmony |
| ONI 유틸리티 | PLib |
| 네트워크 | 기존 프로젝트 네트워크 계층 우선 활용 |
| 로비 | Steam Lobby |
| 연결 | Steam P2P 또는 Steam Datagram Relay |
| 서버 구조 | 호스트 권위형 |
| 저장 | 호스트 로컬 세이브 |
| 버전 관리 | Git, GitHub |
| 개발 도구 | Visual Studio 2022, Claude Code, ILSpy |
| 오류 분석 | ONI Player.log, 구조화 로그 |

## 4.3 서버 구조

초기에는 별도 AWS 서버를 사용하지 않는다.

```text
플레이어 A
게임 클라이언트 + 호스트 서버
        |
        | Steam P2P / Relay
        |
플레이어 B, C, D
게임 클라이언트
```

호스트가 담당하는 작업:

- 명령 유효성 검사
- 소유권 검사
- 최종 게임 명령 실행
- 세이브 생성
- 소유권 데이터 저장
- 클라이언트 하드 싱크
- 플레이어 참가 및 퇴장 관리

## 4.4 명령 동기화

평상시에는 전체 게임 상태가 아니라 플레이어 명령을 전송한다.

동기화 대상:

- 굴착
- 건설
- 해체
- 작업 취소
- 우선순위 변경
- 복제체 이동
- 스킬 설정
- 스케줄 변경
- 프린팅 팟 선택
- 저장고 설정
- 문 권한
- 시간 배속
- 일시정지

기본 흐름:

```text
클라이언트 입력
    ↓
네트워크 명령 생성
    ↓
호스트 전송
    ↓
호스트 권한 검사
    ↓
호스트 명령 실행
    ↓
모든 클라이언트에 결과 전파
```

## 4.5 상태 동기화

ONI 시뮬레이션은 클라이언트마다 오차가 발생할 수 있다.

따라서 아래 방식을 함께 사용한다.

- 실시간 명령 동기화
- 주요 상태 해시 비교
- 일정 주기 세이브 기반 하드 싱크
- 재접속 시 최신 세이브 전송
- 불일치 발생 시 호스트 상태 우선 복구

## 4.6 네트워크 객체 ID

Unity InstanceID는 클라이언트마다 달라질 수 있으므로 네트워크 식별자로 사용할 수 없다.

지속적인 ID가 필요한 객체:

- 프린팅 팟
- 복제체
- 건물
- 저장고
- 로켓
- 자동화 시설
- 공동 프로젝트
- 작업 명령

예시 모델:

```csharp
public readonly record struct PlayerId(ulong Value);

public readonly record struct NetworkObjectId(Guid Value);

public enum OwnershipType
{
    PrintingPod,
    Duplicant,
    Building,
    Storage,
    Rocket,
    SharedProject
}

public sealed class OwnershipRecord
{
    public NetworkObjectId ObjectId { get; init; }
    public PlayerId OwnerPlayerId { get; init; }
    public OwnershipType Type { get; init; }
}
```

## 4.7 소유권 서비스

필요한 핵심 인터페이스:

```csharp
public interface IOwnershipRegistry
{
    bool TryGetOwner(NetworkObjectId objectId, out PlayerId owner);
    void Register(NetworkObjectId objectId, PlayerId owner, OwnershipType type);
    void Transfer(NetworkObjectId objectId, PlayerId newOwner);
    void Remove(NetworkObjectId objectId);
}

public interface IPermissionService
{
    bool CanControlDuplicant(PlayerId playerId, NetworkObjectId duplicantId);
    bool CanModifyBuilding(PlayerId playerId, NetworkObjectId buildingId);
    bool CanUseStorage(PlayerId playerId, NetworkObjectId storageId);
    bool CanPrintDuplicant(PlayerId playerId, NetworkObjectId printingPodId);
}
```

## 4.8 세이브 메타데이터

ONI 기본 세이브와 함께 멀티플레이 메타데이터를 저장한다.

예시:

```json

      "playerId": "steam-id",
      "displayName": "Player A",
      "printingPodId": "pod-uuid",
      "duplicantIds": [
        "duplicant-uuid-1",
        "duplicant-uuid-2"
      ]
    }
  ],
  "ownership": [
    {
      "objectId": "object-uuid",
      "ownerPlayerId": "steam-id",
      "type": "Duplicant"
    }
  ]
}
```

필수 처리:

- 스키마 버전
- 이전 버전 마이그레이션
- 손상 데이터 검증
- 중복 ID 처리
- 접속하지 않은 플레이어 처리
- 삭제된 객체 정리
- 하드 싱크 시 동일 데이터 반영

## 6. Claude Code 활용 방식

## 6.1 역할

Claude Code가 담당할 작업:

- 리포지토리 전체 구조 분석
- 네트워크 흐름 추적
- Harmony 패치 대상 조사
- 구현 계획 작성
- 작은 기능 단위 코드 수정
- 빌드 실행
- 컴파일 오류 분석
- Git diff 검토
- Player.log 분석
- 테스트 케이스 작성
- 문서 업데이트

사용자가 담당할 작업:

- 게임 실행
- 호스트 및 클라이언트 수동 테스트
- 실제 화면과 동작 확인
- 게임 기획 결정
- 충돌 재현
- 테스트 로그 제공
- 최종 코드 검토

## 6.2 기본 작업 원칙

Claude Code에게 큰 기능을 한 번에 구현시키지 않는다.

작업 단위 예시:

```text
좋은 작업:
- 프린팅 팟 생성 시 안정적인 NetworkObjectId를 등록한다.
- 복제체 생성 시 팟 소유권을 상속한다.
- 다른 플레이어의 MoveTo 명령을 호스트에서 거부한다.

나쁜 작업:
- 멀티플레이 소유권 시스템 전체를 완성한다.
- 게임을 4인 멀티플레이로 바꾼다.
```

## 6.3 프로젝트 CLAUDE.md 원칙

저장소 루트의 `CLAUDE.md`에 아래 규칙을 둔다.

- 호스트가 소유권 변경 명령의 최종 권한을 가진다.
- Unity InstanceID를 영구 ID로 사용하지 않는다.
- 네트워크 프로토콜 변경 전 명세를 작성한다.
- 싱글플레이 동작을 유지한다.
- 관련 없는 리팩터링을 하지 않는다.
- 코드 수정 전 실행 경로를 확인한다.
- 수정 후 전체 솔루션을 빌드한다.
- 사용자 승인 없이 commit, push, reset, clean을 실행하지 않는다.
- ONI 원본 DLL을 수정하거나 배포하지 않는다.
- 모든 네트워크 및 권한 오류에 구조화 로그를 남긴다.

| 네트워크 패킷 중복 | 명령 중복 실행 | CommandId와 중복 방지 레지스트리 |
| 권한 검증이 클라이언트에만 존재 | 우회 가능 | 호스트에서 최종 검증 |
| 외부 모드 충돌 | 크래시 및 오동작 | 초기 바닐라 환경 우선 |
| ONI 업데이트 | 패치 실패 | 지원 버전 고정 및 호환성 테스트 |
| 기능 범위 확대 | 프로젝트 장기화 | MVP 비목표 유지 |

## 12. MVP 완료 기준

다음 조건을 모두 충족하면 MVP로 정의한다.

- 2명이 Steam을 통해 같은 게임에 접속할 수 있다.
- 플레이어별 프린팅 팟이 하나씩 존재한다.
- 각 프린팅 팟에서 복제체를 출력할 수 있다.
- 출력된 복제체가 해당 플레이어에게 귀속된다.
- 다른 플레이어의 복제체를 직접 조작할 수 없다.
- 자신의 복제체는 정상적으로 조작할 수 있다.
- 게임 저장 후 소유권이 유지된다.
- 클라이언트 재접속 후 소유권이 유지된다.
- 하드 싱크 후에도 권한이 정상 작동한다.
- 싱글플레이가 기존처럼 작동한다.
- 2인 기준 50주기 플레이가 가능하다.
- 세이브 파일 손상이나 반복적인 치명적 크래시가 없다.

## 14. 최초 실행 작업

프로젝트를 시작할 때 다음 순서로 진행한다.

1. 기존 멀티플레이 프로젝트를 포크한다.
2. 로컬에 clone한다.
3. 기능 브랜치를 만든다.
4. Claude Code를 계획 모드로 실행한다.
5. 기존 프로젝트 구조를 분석한다.
6. 코드 수정 없이 전체 빌드를 성공시킨다.
7. ONI 로컬 모드에 배포한다.
8. 기존 멀티플레이 호스트와 클라이언트를 실행한다.
9. 네트워크 및 세이브 흐름을 문서화한다.
10. 소유권 도메인 모델부터 구현한다.

첫 번째 개발 성공 기준은 프린팅 팟 생성이 아니다.

> 기존 프로젝트를 수정하지 않은 상태에서 빌드하고, 게임에서 정상적으로 실행하는 것이 첫 번째 성공 기준이다.

## 15. 첫 번째 Claude Code 작업 요청

```text
현재 리포지토리를 수정하지 말고 빌드 환경과 코드 구조를 진단해라.

1. 솔루션과 프로젝트 파일을 확인한다.
2. 필요한 .NET Framework, NuGet 패키지, ONI DLL을 정리한다.
3. 서버와 클라이언트 진입점을 찾는다.
4. 플레이어 ID와 네트워크 객체 ID 구조를 찾는다.
5. 명령 패킷의 생성부터 실행까지 추적한다.
6. 세이브 및 하드 싱크 흐름을 추적한다.
7. 프린팅 팟과 복제체 관련 Harmony 패치를 찾는다.
8. 정확한 빌드 명령을 제안한다.
9. 코드 수정 없이 빌드를 시도한다.
10. 실패하면 첫 번째 원인만 분석한다.

추측하지 말고 파일 경로, 클래스, 메서드 이름을 근거로 제시해라.
아직 새로운 기능은 구현하지 마라.
```
